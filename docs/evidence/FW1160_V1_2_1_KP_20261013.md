# FW 11.60 / v1.2.1: reported kernel panic

On 2026-10-13 the user reported a console KP roughly 20–30 seconds after
starting a game while Common FPS v1.2.1 was loaded. After removing that ELF
and rebooting the console, the game ran without KP. This is a useful control
result linking the failure to the counter or its interaction with the setup;
the exact failing operation is not established.

The supplied `CommonFPS_v1_2_1.log` contains five lines, 889 bytes: controller
startup, ShellUI PID 58, and two successful but empty game lookups. It contains
no recorded renderer bootstrap, no game PID and no kernel panic backtrace.
Missing later records cannot prove that those operations never executed:
ordinary buffered appends may be absent after a crash, and this log does not
contain a complete kernel crash report.

The next hardware check uses a distinct observation-only preflight. It links
none of the VideoOut, MDBG, DCE or ShellUI injection adapters, records a bounded
process-list view, and synchronizes log writes before/after each sysctl.
Passing that check will not establish that DCE or rendering is safe: those
require their own subsequent validation.

Until isolated on hardware, neither the existing v1.2.1 nor the full v1.2.3 RC1
renderer should be treated as confirmed for FW 11.60.

## Preflight v0.1 hardware result, 2026-10-14 (Europe/Moscow)

The user supplied `CommonFPS_FW1160_Preflight.log` and reported another
freeze/shutdown, also reproducible after a couple of minutes in the system
menu without starting a game. This is a report of a console failure; the
application log contains no kernel backtrace or exact panic timestamp.

The file is 36,678 bytes / 633 lines, SHA-256
`600bcbc85ea2d99ff0e04ebdeb524991d91f8a834b3fe0bf40c5adcd8a5c0285`.
It identifies Preflight v0.1 and SDK-reported firmware `0x11600005`.
Every tick 0 through 119 has size-before/after, data-before/after and
parse-complete records. All 240 sysctl calls return `rc=0 errno=0`, and all
120 parses report `malformed=0`. The final record is:

```text
stage=observation-complete passive-park=1
```

The log was not truncated by its 64 KiB limit. The program reached the end of
observation and logged its transition to the resident wait loop; this does
not prove that any preceding operation was free of delayed side effects.
No individual failed or hung sysctl is identified by this log.

This binary links no renderer, VideoOut sampler, DCE ioctl, MDBG adapter or
ptrace application path. The report therefore demonstrates a failure in the
reduced configuration as well; those FPS-specific operations are not needed
to reproduce this reported failure. It does not exonerate every path in the
full counter or establish that the loader alone is responsible.

The unmodified SDK v0.41 CRT remains shared startup code. Before `main`,
`payload_init` runs `__kernel_init`, `__patch_init` and `__rtld_init`.
`__patch_init` uses kernel RW to update its own process credentials and
syscall permissions. Thus application-level markers such as
`auth_changes=disabled` are not a claim that the entire ELF performs no
kernel writes. Upstream source references:

- https://github.com/ps5-payload-dev/sdk/blob/v0.41/crt/crt.c
- https://github.com/ps5-payload-dev/sdk/blob/v0.41/crt/patch.c

At tick 20 a raw `eboot.bin` match occurs at byte 394 in a record whose
legacy name is `SceMediaCoreServer`, PID 64. A scan hit is not an identified
game process or proof of a changed process-name offset. Do not promote that
offset into the runtime game detector.

Keep v1.2.1, RC1, RC2 and Preflight v0.1 disabled on FW 11.60, including
autoload, and do not ask the user to repeat the failing preflight. RC2's
application hold cannot prevent SDK startup that already happened before it.
Before choosing another diagnostic boundary, obtain the exploit chain and
versions, ELF launch method/loader version, and other active/autoloaded
payloads. Retain the earlier removal/reboot control result as evidence.

## Autoload configuration received, 2026-10-14

The user identified FW 11.60 and WebKit Autoloader v0.5.2, and supplied the
actual 150-byte `autoload.txt`, SHA-256
`f073d9ba984b7315d69c07fbc2b58c6bdb3f52322749e743d98a229238332140`:

```text
!1000
elfldr-ps5.elf
!3000
ftpsrv-ps5.elf
!1000
shadowmountplus.elf
!3000
kstuff-fpkg-1.13-dr-test6.elf
!3000
Common_FPS_PS5_FW1160_Preflight_v0.1.elf
```

Preflight is therefore configured to launch after kstuff in this setup.
That order is a relevant interaction hypothesis, not an established cause
of KP. Do not infer a universal rule that every kstuff variant on every
loader must run last from a report about a different exploit/loader.

Upstream WebKit Autoloader v0.5.2 supports custom ELF loaders listed in
`autoload.txt`; the presence of `elfldr-ps5.elf` alone is not a configuration
error. The pinned elfldr v0.26 source creates a new socket pair and a pipe in
each target payload process (`elfldr_payload_args`). It does not substantiate
a claim that all these payloads necessarily share one kernel RW pipe.
The user's manually supplied `elfldr-ps5.elf` has not yet been inspected, so
its actual version and ABI cannot be identified from its basename.

References:

- https://github.com/itsPLK/ps5-webkit-autoloader/blob/v0.5.2/README.md
- https://github.com/ps5-payload-dev/elfldr/blob/v0.26/elfldr.c

A control config was prepared by commenting only the Preflight entry.
The other four payload names, their order and every existing delay are
preserved; no ELF is added or replaced. The user must fully reboot to remove
the already resident diagnostic before assessing stability without it.
This config is not a counter fix or a claim that the other payloads are safe.

The remaining read-only inputs are the actual `elfldr-ps5.elf` and
`kstuff-fpkg-1.13-dr-test6.elf` from the active autoload directory. The exact
DR test6 build is not represented by the older public release artifacts
examined in drakmor/kstuff-lite, so do not substitute a different kstuff
build's source as proof of its runtime behavior. A new test of Preflight
before kstuff has not been requested.
